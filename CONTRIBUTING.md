# Contributing to Lightnix

First of all, thank you for your interest in Lightnix.

Lightnix is currently in the concept and design stage.

The goal is not only to build another Linux distribution, but to explore a different way of thinking about operating systems:

> What if an operating system only existed for the task you are performing right now?

At this stage, ideas and discussions are often more valuable than code.

---

# Current Status

⚠️ Early Concept Stage

Many parts of the system remain undefined:

* Runtime architecture
* Filesystem composition
* Snapshot design
* Package management
* Hot switching mechanisms
* Security model

Nothing is considered final.

Contributors are encouraged to challenge assumptions and propose alternatives.

---

# Ways to Contribute

There are many ways to help.

## 💡 Share Ideas

The easiest way to contribute.

Open an Issue if you have thoughts about:

* System architecture
* User experience
* Boot flow
* Package management
* Snapshots
* Security
* Performance

Even simple questions can lead to better designs.

---

## 🏗 Improve the Design

Lightnix needs design discussions around:

* Buildroot integration
* OverlayFS usage
* SquashFS composition
* Namespace isolation
* Runtime switching
* Snapshot implementation

Design proposals are highly welcome.

---

## 📚 Improve Documentation

Good documentation is often more valuable than code.

You can help by:

* Fixing grammar
* Improving explanations
* Creating diagrams
* Writing technical notes
* Expanding design documents

---

## 🧪 Research Existing Solutions

Many ideas in Lightnix overlap with existing technologies.

Research contributions are welcome.

Examples:

* NixOS
* GNU Guix
* Fedora Silverblue
* Alpine Linux
* Docker
* Podman
* Unikernels
* LiveCD systems

If you find similar projects or relevant papers, please share them.

---

## 💻 Contribute Code

Once implementation begins, code contributions will become increasingly important.

Potential areas include:

* Buildroot packages
* RootFS tooling
* Snapshot systems
* Package manager development
* Bootloader integration
* Runtime orchestration

---

# Before Opening an Issue

Please check whether the topic has already been discussed.

When possible, include:

* clear descriptions
* use cases
* technical reasoning
* references to existing solutions

Constructive disagreement is welcome.

---

# Pull Requests

For now:

1. Fork the repository.
2. Create a feature branch.
3. Make your changes.
4. Submit a Pull Request.

Please explain:

* what changed
* why it changed
* any trade-offs involved

---

# Design Principles

When proposing ideas, try to align with the project's goals:

* Simplicity over complexity
* Task-oriented workflows
* Minimal dependencies
* Fast startup
* Small attack surface
* Recoverability
* Modularity

These principles are guidelines, not strict rules.

---

# Code Style

There is currently no strict coding standard.

General expectations:

* Keep code simple.
* Prefer readability.
* Avoid unnecessary abstractions.
* Document non-obvious decisions.

Future coding standards may be added as the project grows.

---

# Code of Conduct

Be respectful.

Everyone is welcome regardless of:

* experience level
* programming language preferences
* operating system background

Healthy technical debate is encouraged.

Personal attacks are not.
